# experiments/ —— 可复现的对照实验（不是「跑一下就完」的脚本）

这个目录放**能复现出数字的实验**：每个实验都有对照组、口径说明、原始数据落盘，
以及一份写明「这轮测了什么 / 没测什么」的报告。

| 实验 | 目录 | 产物 | 一句话 |
|---|---|---|---|
| 上下文压缩的**质量代价** | `context_compression/` | `results/context_compression_baseline.{csv,json,md}` | 同一批任务 × 若干压缩档位，把「省了多少」和「代价是什么」一起量化 |

## 1. 上下文压缩代价对照实验（`context_compression/`）

### 1.1 为什么做

README §5.6 原来只说「压缩省了 31.0% 字符」——**只报好处不报代价**，
读者无法判断这个取舍值不值。本实验把另一半补上：压缩开 / 关跑同一批任务，
比较**字符节省、成功率、平均步数、token、答案要点命中率、工具调用参数被压坏的次数**。

### 1.2 怎么跑

```bash
# 在仓库根目录（本机 venv 已装好依赖；RAG 走进程内直连，不需要起 MCP 子进程）
.venv\Scripts\python.exe experiments\context_compression\run_experiment.py

# 参数
#   --limit N        本批跑多少条任务（默认 20，0 = 全部）
#   --rag-mode       auto | mcp | direct（默认 direct：进程内直连，省掉每任务 5s 的子进程启动）
#   --baseline NAME  产物文件名（默认 context_compression_baseline）
```

产物落在 `experiments/results/`：

- `*.csv` —— **逐任务原始数据**（每个档位一行：状态、步数、压缩前后字符、token、要点命中、参数差异）；
- `*.json` —— 元信息（跑的时间、代码基线 commit、端点探测结果、档位定义、各档汇总、参数差异明细）；
- `*.md` —— 人读的取舍曲线报告（结论段由数字自动生成，不写死）。

> **trace 不进仓库**：逐任务 trace 落在系统临时目录（`tempfile.mkdtemp`），
> 避免把本机绝对路径写进提交物；需要的数字已经全部落进上面的 CSV / JSON。

### 1.3 实验设计（受控变量）

| 维度 | 怎么控的 |
|---|---|
| 任务批次 | 评测集里**期望用到检索工具**的题目（检索结果动辄上千字符 → 才有长上下文可压）；同一批任务跑遍所有档位 |
| 工具计划 | 只由**任务文本**决定。任务文本永远在消息列表第一条，`compress_messages` 永远原样保留 → 各档位计划完全一致 |
| 唯一的变量 | 上下文被压掉多少（`agent.max_context_chars` + `agent.context_keep_last` 两个开关） |
| 对照组 | `off` 档：预算设成无限大 → `compress_messages` 直接返回原消息，不压 |

档位（`(context_keep_last, max_context_chars)`）：

| 档位 | 含义 |
|---|---|
| `off` | 对照组：完全不压缩 |
| `default` | 仓库默认档（12000 字符 / 保留最近 6 条） |
| `keep2_4000` / `keep2_2000` / `keep2_1200` | 收紧档：保留最近 2 条，预算逐级收紧 |
| `keep1_800` | 极紧档：保留最近 1 条，预算 800 |

### 1.4 被测模型：**脚本化假模型**（本轮没有真端点）

**先探测再决定**：脚本启动时会探测端点（`OPENAI_BASE_URL` / `OPENAI_API_KEY` / `MODEL` 是否配置、
能不能连通），并把探测结果写进产物的 `meta.endpoint_probe`。
本机探测结果：**没有可用端点**（仓库没有 `.env`，环境变量未配置，本地也没有推理服务）——
所以**本轮不测真实模型的语义质量**，改用仓库自带的脚本化假模型
（`tests/fake_llm.py` 的 `ScriptedChatModel`，本目录扩展成上下文忠实的 `ContextFaithfulFakeModel`）。

假模型不是「无视上下文吐固定答案」的那种（那样压缩与否答案完全一样，实验没意义），
它**只按看得见的东西决策**：

1. 看得到哪些工具已经返回结果 → 决定下一步调哪个；
2. 计算器的表达式取**检索结果里的数字** → 检索结果被压掉，参数就退化成占位值；
3. 最终答案复述**当前看得见的**观察内容 → 观察被压短，答案要点就丢。

> ⚠️ 这是**探针式设计**：目的是把「信息损失」放大成可测量的差异，
> **不是**在模拟真实模型的语义能力。
> **本轮只测机械效果（压缩 / 步数 / token）与「上下文信息损失对答案要点的代理影响」，未测语义质量。**
> 真实端点的语义质量曲线留给有 key 的环境（用 `scripts/eval_agent.py` 跑同一批评测集）。

### 1.5 实测结果（`results/context_compression_baseline.md` 有完整表格）

34 条任务 × 6 个档位，本机实跑：

| 档位 | 成功率 | 平均步数 | token 省下 | 答案要点命中率 | 要点全中率 | 工具参数被压坏 |
|---|---|---|---|---|---|---|
| `off` | 34/34 | 2.68 | — | 0.7581 | 0.5882 | 0 |
| `default`（仓库默认） | 34/34 | 2.68 | 0.0 | 0.7581 | 0.5882 | 0 |
| `keep2_4000` / `keep2_2000` | 34/34 | 2.68 | 0.0 | 0.7581 | 0.5882 | 0 |
| `keep2_1200` | 34/34 | 2.68 | **0.2927** | **0.6129** | **0.4118** | **5** |
| `keep1_800` | 34/34 | 2.68 | 0.2808 | 0.6129 | 0.4118 | 5 |

三条结论：

1. **默认档根本没触发压缩**（token 省下 0.0）→ 默认配置下的「压缩」目前只是一道没被用上的保险；
2. **一压就压狠**：预算收到 1200 字符时，实际送进模型的上下文少 29.3%，代价是
   答案要点命中率 0.7581 → 0.6129、5 次工具调用参数被压坏（`(0-16)` → `(0-0)`，检索到的值丢了）；
3. **成功率与步数没变**（34/34、2.68）→ 这批任务里压缩不影响「跑不跑得完」，影响的是「答得全不全」。

### 1.6 局限（如实说）

- **假模型**：见 §1.4——测的是信息损失，不是语义质量；
- **单一知识库 / 5 篇文档**：结论与这个知识库的长度分布有关；
- **token 是字符代理**（1 字符 ≈ 1 token），不是真实 tokenizer 计数；
- **要点命中率是关键词命中**，同义改写会漏判（见 README §5.9.4）；
- **参数压坏的判定是「与对照组逐条比对」**：同一批任务、同一策略下唯一的变量是上下文，
  参数变了就说明是被压缩改的——但**参数「变了」不等于参数「错了」**（这里确实是退化了：`(0-16)` → `(0-0)`）。
